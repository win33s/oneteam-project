# 설계 (2026-10-01)

기획(`기획.md` v2)을 데모로 구현한 구조와 결정 사항입니다. 서비스 이름은 HBM(Happy Bonding Memory)입니다.

## 결정 사항

| 항목 | 결정 | 이유 |
|---|---|---|
| 프론트엔드 | React + Vite | 팀원이 화면 단위로 나눠 작업하기 쉬움 |
| 서버 | Node(Express), JSON 파일 저장 | 설치할 DB 없이 바로 실행 |
| 에이전트 판단 | 규칙 기반이 기본, Claude API는 선택 연동 | 키 없이도 데모가 항상 같은 결과로 동작 |
| 사내 시스템 | ERP·캘린더·조직도·메일·후기 폼을 모두 가상으로 구현 | 실제 사내 시스템에는 접근할 수 없음 |
| 데이터 | 부서·인물·장소·경비 모두 지어낸 값 | 실제 업체에 가짜 후기가 붙지 않도록 함 |

## 구성

```
agent/
├─ server/
│  ├─ index.js          로컬 서버 시작, 10초 주기 동기화
│  ├─ app.js            Express 앱 조립 (로컬 서버와 Vercel 함수가 함께 사용)
│  ├─ erp.js            Mock ERP 화면 (서버 렌더링 HTML: 목록, 상세, 신규 등록)
│  ├─ api.js            화면이 쓰는 REST API
│  ├─ seed.js           가상 데이터 생성 (부서, 구성원, 장소, 18개월치 전표, 캘린더)
│  ├─ db.js             저장소 (로컬: data/db.json, Vercel: Upstash Redis), 에이전트 로그
│  └─ agent/
│     ├─ crawler.js     ERP 화면 크롤러 (cheerio)
│     ├─ records.js     전표 → 부서 활동 기록 변환, 알림·후기 폼 메일
│     ├─ scheduler.js   날짜 추천
│     ├─ recommender.js 장소 추천, 첫 화면 추천 줄
│     ├─ weather.js     가상 날씨 예보
│     ├─ mailer.js      Mock 메일 발송
│     └─ llm.js         Claude API 선택 연동
└─ client/src/
   ├─ pages/            Login, Home, PlanPage, VotePage, VenuePage, History, ActivityPage, Explore, Mailbox, ReviewForm, Profile
   └─ components/       VenueCard(카드·캐러셀), AgentLog
```

## 실행 환경 두 가지

| | 로컬 (`npm start`) | Vercel |
|---|---|---|
| 진입점 | `server/index.js` | `api/index.js` (서버리스 함수), 화면은 정적 배포 |
| 저장 | `data/db.json` 파일 | Upstash Redis의 `hbm:db` 키에 전체 데이터를 JSON으로 저장 |
| ERP 화면 읽기 | 자기 서버의 ERP 화면에 HTTP로 접속 | 같은 화면 HTML을 함수 안에서 만들어 읽음 |
| 새 전표 확인 | 10초 타이머 | 화면이 상태를 조회할 때 |

요청마다 저장소에서 읽고, 바뀐 내용이 있을 때만 응답 직전에 저장한다. 전체 데이터를 한 덩어리로 읽고 쓰므로 동시에 여러 명이 저장하면 한쪽 변경이 덮일 수 있다. 시연 규모를 전제로 한 구조다.

## 에이전트 동작

### 1. ERP 크롤링 (`crawler.js`, `records.js`)

- API가 아니라 ERP **화면(HTML)** 을 읽는다. 목록 페이지를 넘기며 전표번호를 모으고, 계정코드가 회의비(53210) 또는 복리후생비-조직활성화(52140)인 새 전표만 상세 화면을 열어 필드를 읽는다. 사무용품비·출장비 등은 제외한다.
- 읽는 필드: 전표번호, 사용일, 부서, 기안자, 계정명·계정코드, 예산구분(팀장 배정 예산 / 부서 공통 예산), 제목, 거래처, 품목, 용도, 구입·소비 내역, 인원, 금액.
- 서버 최초 실행 시 전체 이력을 한 번 수집해 부서별 활동 기록을 만든다. 담당자가 입사하기 전 기록도 여기서 생긴다.
- 이후 10초마다 새 전표를 확인한다. 새 전표가 나오면 활동 기록을 만들고, 확정된 기획과 장소·날짜가 맞으면 연결하고, 담당자에게 기록 업데이트 메일을 보낸다. 담당자가 기획 확정 때 후기 폼 발송에 동의했으면 참석자에게 후기 폼 메일도 보낸다.
- 처음 보는 거래처는 품목·제목 키워드로 유형을 추정해 장소 DB에 새로 등록한다.

### 2. 날짜 추천 (`scheduler.js`)

- 조직도에서 고른 부서원의 캘린더(휴가·출장·교육·야간 근무)와 부서 과제 일정을 본다.
- 중요한 과제 일정(`important`)과 겹치는 기간은 후보에서 제외하고, 제외한 기간을 화면에 알려 준다.
- 점수 = 참석 가능 비율 + 요일 가산점 − 과제 일정 근접 감점 − 팀장 불참 감점. 주말과 공휴일은 제외한다.
- 상위 6개를 근거(누가 왜 안 되는지, 어느 과제 일정과 가까운지)와 함께 보여 준다.

### 3. 날짜 투표

- 후보를 2개 이상 고르면 선택한 부서원 전원에게 투표 메일을 보낸다.
- 담당자 화면은 2.5초마다 결과를 다시 불러와 실시간으로 보여 준다.

### 4. 장소·활동 추천 (`recommender.js`, `weather.js`)

점수에 들어가는 근거:

- 이맘때(같은 계절) 우리 부서와 타부서가 방문한 횟수 (경비 전표 기준)
- 후기 평점
- 사내 블로그·동아리 게시판의 단체 사진 게시글 수
- 활동일 날씨 예보 (야외 활동은 맑을 때 가산, 비·눈이면 감점)
- 1인당 평균 경비와 예산
- 개인 프로필 (채식, 해산물·매운 음식 불가, 음주 여부, 선호 유형)
- 수용 인원

우리 부서가 3번 이상 간 곳은 조금 감점하고 새로운 곳을 보라고 안내한다. 어느 부서도 가 본 적 없는 곳은 본 추천과 분리해 "완전히 새로운 제안"으로 따로 뽑으며, 경비 기록이 없으므로 날씨와 취향만 근거로 삼는다.

각 추천에는 경비 기록(부서, 사용일, 금액, 계정, 예산구분), 후기, 담당자 팁, 사진 게시글 출처를 근거로 붙인다. 장소 상세 화면에는 부서별 방문 횟수를 보여 준다.

첫 화면의 각 카드에는 그 줄에서 뽑힌 이유를 한 줄로 붙인다 ("타부서 평점 TOP 1!", "지금 시즌엔 여기!" 등).

### 4-1. 후기 폼

날짜와 장소를 확정하면 "후기 폼을 작성해 발송할까요?"를 담당자에게 묻는다. "네"를 고르면 폼을 준비해 두고, ERP 전표가 감지되어 활동 기록이 생길 때 참석자에게 발송한다. 기획 없이 올라온 기록은 기록 화면에서 같은 질문을 한다.

### 4-2. 로그인과 소속

1번 화면에서 사번·이름·비밀번호의 형식만 확인하고(비밀번호는 저장하지 않음), 2번 화면에서 그룹과 팀을 고른다. 고른 팀에 같은 이름의 구성원이 있으면 그 사람으로, 없으면 새 구성원으로 등록한다. 이후 화면은 `x-emp-id` 헤더로 사용자를 구분하고, 우리 부서 기준(기록, 추천, 기획 목록)이 그 사람의 팀으로 바뀐다. 실서비스에서는 사내 SSO로 교체한다.

### 5. Claude API 선택 연동 (`llm.js`)

`ANTHROPIC_API_KEY`가 있을 때만 켜진다. 없으면 규칙 기반 결과를 그대로 쓴다.

- 첫 화면 자유 입력을 기획 조건(유형, 예산, 기간)으로 해석
- 추천 결과에 대한 3~4문장 조언 작성 (주어진 근거 데이터만 사용)

## 실제 사내 적용 시 바꿀 부분

| 데모 | 실제 |
|---|---|
| `erp.js` Mock 화면 | 사내 ERP 화면 또는 API. `crawler.js`의 선택자와 로그인 처리만 교체 |
| `seed.js`의 캘린더·조직도 | 사내 캘린더·조직도 연동 |
| `mailer.js` 데모 메일함 | 사내 메일 발송 |
| `/review/:id` 데모 폼 | 네이버 폼 생성·응답 수집 |
| `seed.js`의 사진 게시글 | 사내 블로그·동아리 게시판 단체 사진 수집 |
| `weather.js` 가상 예보 | 기상청 예보 API |
| 사번·이름·비밀번호 형식 확인 | 사내 SSO |
| `data/db.json` 또는 Redis 한 덩어리 저장 | 사내 DB (테이블 단위 저장) |
