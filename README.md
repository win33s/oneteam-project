# 6인 AI 활용 GitHub 협업 지침

## 1. 기본 원칙

* `main` 브랜치에는 직접 커밋하거나 푸시하지 않는다.
* 한 작업은 하나의 Issue, 하나의 브랜치, 하나의 Pull Request로 관리한다.
* 작업을 시작하기 전에 담당자와 수정할 파일 범위를 공유한다.
* 같은 브랜치를 여러 사람이 동시에 사용하지 않는다.
* AI가 작성한 코드도 작업자가 직접 검토하고 책임진다.

## 2. 작업 시작 절차

1. GitHub Issue를 생성한다.
2. Issue에 다음 내용을 작성한다.
   * 작업 목적
   * 담당자
   * 수정 예정 파일 또는 폴더
   * 연관된 기능이나 주의사항
3. 다른 사람과 수정 범위가 겹치지 않는지 확인한다.
4. 최신 `main`을 받은 후 작업 브랜치를 생성한다.

```
git switch main
git pull --ff-only
git switch -c feature/작업명
```

브랜치 이름 예시:

```
feature/login-api
feature/login-ui
fix/session-timeout
refactor/user-service
docs/setup-guide
```

## 3. 작업 배분 규칙

* 6명 모두 자신의 담당 Issue와 브랜치를 사용한다.
* 가능하면 기능뿐 아니라 수정할 폴더나 파일 기준으로 영역을 나눈다.
* 공통 파일을 수정해야 하면 작업 전에 팀에 알린다.
* 같은 파일을 수정해야 하는 작업은 동시에 진행하지 말고 순서를 정한다.
* 각 구성원은 진행 중인 핵심 작업을 가급적 한 개로 제한한다.
* 작업 도중 수정 범위가 확대되면 먼저 Issue와 팀 채널에 기록한다.

## 4. AI 도구 사용 규칙

AI에게 작업을 요청할 때 수정 범위를 명확하게 지정한다.

예시:

```
src/auth 폴더만 수정하세요.
공통 컴포넌트와 설정 파일은 변경하지 마세요.
관련 없는 리팩터링이나 전체 코드 포맷팅은 하지 마세요.
작업 후 변경한 파일과 변경 이유를 정리하세요.
```

AI 작업이 끝나면 담당자가 반드시 다음 사항을 확인한다.

* `git diff`로 전체 변경 내용 확인
* 요청하지 않은 파일이 수정되지 않았는지 확인
* 기존 기능이 삭제되거나 덮어써지지 않았는지 확인
* 비밀번호, API 키, 개인정보가 포함되지 않았는지 확인
* 테스트·빌드·린트·타입 검사가 통과하는지 확인
* 사용하지 않는 코드나 디버깅 코드가 남아 있지 않은지 확인

AI가 만들었다는 이유로 변경사항을 검토하지 않고 커밋하거나 병합해서는 안 된다.

## 5. 충돌 가능성이 높은 파일

다음 파일은 동시에 수정하지 않는 것을 원칙으로 한다.

* `package.json`, `package-lock.json` 등 의존성 파일
* 프로젝트 설정 파일
* 공통 타입 및 인터페이스
* 공통 컴포넌트
* 전역 CSS 및 디자인 토큰
* DB 스키마 및 마이그레이션
* API 명세
* 환경설정 파일
* 자동 생성 파일

이러한 파일을 수정할 때는 담당자를 한 명 정하거나 별도 PR로 분리한다.

## 6. 커밋 규칙

* 커밋은 작고 명확한 단위로 나눈다.
* 기능 구현, 리팩터링, 포맷 변경을 하나의 커밋에 섞지 않는다.
* 커밋 메시지만 보고 변경 목적을 알 수 있게 작성한다.

커밋 메시지 예시:

```
feat: 로그인 API 구현
fix: 세션 만료 처리 오류 수정
refactor: 사용자 조회 로직 분리
test: 로그인 실패 테스트 추가
docs: 로컬 실행 방법 추가
chore: 인증 라이브러리 버전 업데이트
```

## 7. Pull Request 규칙

PR에는 다음 내용을 작성한다.

* 작업 목적
* 주요 변경사항
* 수정한 파일 또는 영역
* 테스트 방법과 결과
* 확인이 필요한 부분
* 관련 Issue 번호
* AI 도구 사용 여부

PR은 가능한 한 작게 유지한다. 관련 없는 수정은 별도 PR로 분리한다.

모든 PR은 최소 1명의 다른 팀원이 리뷰한 후 병합한다. 공통 설정, DB 스키마, 보안 및 핵심 구조 변경은 가능하면 2명이 검토한다.

## 8. 병합 전 최신화

PR을 올리기 전 최신 `main`을 반영한다.

```
git fetch origin
git rebase origin/main
```

충돌이 발생하면 다음 원칙을 따른다.

* AI에게 충돌 해결을 전부 맡기지 않는다.
* 양쪽 변경 목적을 먼저 확인한다.
* 상대방의 코드를 임의로 삭제하지 않는다.
* 판단하기 어려우면 해당 코드를 작성한 사람과 함께 해결한다.
* 충돌 해결 후 테스트를 다시 실행한다.
* 해결 결과를 `git diff`로 확인한다.

## 9. 동시 작업 환경

한 사람이 여러 AI 도구를 동시에 사용할 경우, 같은 폴더에서 실행하지 않는다. 각 작업마다 별도 브랜치와 `git worktree`를 사용한다.

```
git worktree add ../project-login-api -b feature/login-api
git worktree add ../project-login-ui -b feature/login-ui
```

각 AI는 자신에게 배정된 작업 폴더만 사용해야 한다.

## 10. 병합 완료 기준

다음 조건을 모두 만족해야 `main`에 병합할 수 있다.

* 담당자가 전체 변경사항을 검토함
* 다른 팀원의 코드 리뷰가 완료됨
* 리뷰 의견이 모두 해결됨
* 빌드가 성공함
* 테스트가 통과함
* 린트 및 타입 검사가 통과함
* 충돌이 해결됨
* 비밀정보가 포함되지 않음
* 관련 Issue와 PR 설명이 최신 상태임

## 11. GitHub 저장소 설정

저장소 관리자는 `main` 브랜치에 다음 보호 규칙을 적용한다.

* 직접 푸시 제한
* PR을 통한 병합만 허용
* 최소 1명 이상의 승인 필요
* 테스트와 빌드 통과 필수
* 해결되지 않은 리뷰 의견이 있으면 병합 금지
* 가능하면 강제 푸시 금지

## 12. 전체 작업 흐름

```
Issue 생성
→ 담당자 및 수정 범위 지정
→ 최신 main에서 개인 브랜치 생성
→ AI를 이용해 제한된 범위만 수정
→ 담당자가 diff와 테스트 결과 확인
→ 작은 단위로 커밋
→ Pull Request 생성
→ 다른 팀원이 코드 리뷰
→ 최신 main 반영 및 충돌 해결
→ 자동 검사 통과
→ main에 병합
→ 관련 Issue 종료
```

가장 중요한 네 가지 원칙은 다음과 같다.

1. 같은 브랜치를 공유하지 않는다.
2. 작업 전에 담당 파일 범위를 정한다.
3. 작고 독립적인 PR을 만든다.
4. AI 코드도 사람이 최종 검토하고 책임진다.
